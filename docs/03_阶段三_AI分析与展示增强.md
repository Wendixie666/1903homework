# 阶段 3：AI 分析、矛盾检测与展示增强

## 目标

前两个阶段解决的是：

- 数据结构化
- Evidence trace-back
- 搜索
- Candidate Compare

阶段 3 再加入真正体现 AI 辅助价值的功能：

**AI 总结、亮点、矛盾、待核实项、面试追问问题，以及更直观的可视化。**

原则：

> AI 分析必须建立在结构化事实和 evidence 上，而不是重新自由发挥。

---

## 3 人分工

### A：AI 分析 / Skill

负责：

- Candidate Summary
- Strengths
- Conflicts / inconsistencies
- Items to verify
- Interview Questions
- 分析结果与 evidence 绑定

可以把不同分析拆成独立 Prompt / Skill。

---

### B：分析后端 / 缓存 / Token 优化

负责：

- AI 分析调用接口
- 将分析结果缓存
- 避免每次刷新页面都重新请求模型
- PDF 前置结构化
- 只把必要结构化内容送给模型
- 记录分析版本 / 时间

---

### C：高级展示

负责：

- Highlight / Conflict / Verify 的视觉区分
- 点击展开详情
- 雷达图或维度展示
- Candidate Compare 中突出差异
- Interview Questions 区域
- AI Analysis 与事实信息明确分开

---

# 实施流程

## Step 1：先区分 Fact 与 AI Analysis

页面和数据结构中必须明确：

```text
Fact
AI Analysis
```

不能把 AI 推断混进事实字段。

建议：

```json
{
  "facts": {},
  "ai_analysis": {
    "summary": "",
    "strengths": [],
    "conflicts": [],
    "items_to_verify": [],
    "interview_questions": []
  }
}
```

---

## Step 2：实现 AI Summary

输入尽量使用已经结构化的数据，而不是重新把所有 PDF 全塞给模型。

输入：

```text
Candidate structured profile
+
selected evidence
```

输出：

```text
Research trajectory
Main strengths
Important context
Uncertain points
```

AI 输出需要保存：

```text
analysis_type
generated_at
model
related_evidence_ids
```

---

## Step 3：实现矛盾检测

重点检查不同材料之间的冲突：

例如：

```text
CV：2023–2025
Personal Website：2022–2025
```

系统不要决定哪个一定正确。

应该生成：

```text
Conflict detected

Source A:
CV p.2 → 2023–2025

Source B:
Personal Website → 2022–2025

Status:
Needs verification
```

---

## Step 4：实现亮点与待核实项

亮点示例：

```text
- 多篇与 LLM for Software Engineering 相关论文
- 有公开代码项目
- 有明确 PI / Co-PI 项目经历
```

但每个亮点最好能对应到具体记录。

待核实：

```text
- Cover Letter 提到某项成果，但 CV 未找到对应记录
- 某项 award 暂未找到公开网页
```

---

## Step 5：实现 Interview Question Skill

目标不是自动评价候选人，而是帮助 reviewer 找到值得继续确认的问题。

输入：

```text
Candidate profile
+
conflicts
+
uncertain items
+
important claims
```

输出：

```text
Question
Reason
Related evidence
```

例如：

```text
问题：
您在 Research Statement 中提到负责 X 项目的核心模型设计，
能否具体说明您个人负责的部分？

原因：
目前材料确认了项目参与，但个人贡献边界不清晰。

证据：
research_statement.pdf p.3
```

---

## Step 6：加入雷达图 / Dimension View

雷达图必须放到最后。

第一版可以只做：

```text
Research
Teaching
Funding
Open Source
Service
```

但需要注意：

1. 每个维度必须有明确计算规则。
2. 如果没有成熟规则，可以先展示“指标值”而不是总评分。
3. 不要让 AI 凭感觉直接生成 0–100 分。
4. 页面中说明维度的数据来源。

更稳妥的第一版：

```text
Publications: 12
First-author: 5
Funding roles: 2
Open-source projects: 3
Teaching records: 4
```

然后再决定是否映射成 radar score。

---

## Step 7：Token 优化

不要重复把 PDF 原文传给模型。

推荐：

```text
PDF
 ↓
一次性解析
 ↓
Structured Candidate JSON
 ↓
Evidence chunks
 ↓
AI Analysis
```

后续 AI 任务优先读取：

```text
Candidate JSON
+
必要 evidence
```

而不是全部 PDF。

# 可直接交给 Codex / AI 的提示词

```text
我们已经完成前两个阶段：

阶段 1：
上传材料
→ Candidate JSON
→ Candidate Profile
→ Evidence trace-back

阶段 2：
多个 Candidate
→ 标签筛选
→ 自然语言筛选
→ Candidate Compare

现在实现阶段 3。

目标是增加 AI-assisted analysis，但必须保持“事实”和“AI 分析”严格分离。

需要实现：

1. Candidate AI Summary
2. Strengths
3. Conflicts / inconsistencies
4. Items to verify
5. Interview Questions
6. 更清晰的视觉展示
7. 可选的 dimension / radar visualization

核心规则：

- AI 分析必须基于已有 Candidate structured data 和 evidence。
- 不要把 AI 推断写回事实字段。
- 每个重要分析结果尽量关联 evidence_ids。
- 不确定信息应该标记为 needs verification。
- 如果两个来源冲突，保留两个版本，不要自动选择一个覆盖另一个。
- AI 分析结果需要缓存，页面刷新不要重复调用模型。
- 尽量复用阶段 1 已经解析好的结构化数据，避免反复把完整 PDF 发送给模型。

Interview Question 功能建议输出：

{
  "question": "",
  "reason": "",
  "related_evidence_ids": []
}

重点让问题围绕：

- 材料中的矛盾
- 个人贡献不清晰
- 很重要但证据不足的 claim
- 值得深入确认的项目或成果

关于雷达图：

不要让 LLM 凭感觉直接给候选人打 0–100 分。

优先使用可解释的客观指标或明确规则。如果当前还没有可靠评分规则，可以先展示各维度指标，不强行计算综合分。

暂时不要为了高级效果大规模重构系统。

请先检查现有代码，说明哪些模块可以直接复用，然后按最小增量方式实现。
```
